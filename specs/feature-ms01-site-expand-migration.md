## Feature: Add the site dimension beside the existing constraints

### Problem Statement

ADR 0012 puts 43logistics.vn, avlogistics.vn and later gtlogistic.vn on one Supabase database. Site-owned rows (settings, pages, menus, posts, testimonials, redirects, leads, contact events) need a `site` dimension before any site-aware code (MS-02) can exist.

Roadmap MS-01 is the **expand** step of ADR 0012 Decision 2. It is additive only: new columns default to `43l` and new constraints sit **beside** the old ones, so the live 43 app (which never reads `site`) and every existing upsert behave exactly as before. The constraint switch is MS-03, and AV/GT rows come after it.

### Proposed Solution

One migration `0014_site_expand` (generated by `pnpm db:generate`, hand-checked) plus the matching Drizzle schema declarations. No query, action, seed or UI change.

1. **Enum** `site` (`43l`, `av`, `gt`) in `db/enums.ts`.
2. **`site site NOT NULL DEFAULT '43l'`** on these tables:

   | Module | Tables |
   | --- | --- |
   | settings | `site_settings` |
   | content | `pages`, `page_translations`, `menu_items`, `menu_item_translations`, `posts`, `post_translations`, `categories`, `category_translations`, `post_categories`, `faqs`, `faq_translations`, `testimonials`, `testimonial_translations` |
   | seo | `redirects` |
   | leads | `leads`, `lead_events` |
   | contact | `contact_events` |

   - `faqs` gets the column on every row for now. Route-bound FAQs become shared (`site` NULL plus a check constraint) in MS-03, because a conditional default is impossible while the old app inserts FAQs without `site`.
3. **Parent keys for composite foreign keys:** unique `(id, site)` on `pages`, `menu_items`, `posts`, `categories`, `faqs`, `testimonials`, `leads`.
4. **New site-inclusive uniqueness**, added beside the old constraints:

   | Table | New unique index | Old constraint that stays until MS-03 |
   | --- | --- | --- |
   | `site_settings` | `(site, key)` | primary key `key` |
   | `pages` | `(site, key)` | `key` unique |
   | `page_translations` | `(site, locale, slug)` | `page_tr_locale_slug_uq` |
   | `menu_items` | `(site, menu, key)` | `menu_items_menu_key_uq` |
   | `post_translations` | `(site, locale, slug)` | `post_tr_locale_slug_uq` |
   | `category_translations` | `(site, locale, slug)` | `cat_tr_locale_slug_uq` |
   | `redirects` | `(site, source_path)` | primary key `source_path` |

5. **Composite foreign keys** `(child_col, site) → parent(id, site)`, added beside the existing single-column foreign keys. `ON DELETE` copies today's key exactly:
   - `CASCADE`: every translation table, `menu_items.parent_id`, both `post_categories` keys and `faqs.page_id`;
   - `NO ACTION`: `pages.parent_id`, `menu_items.page_id` and `lead_events.lead_id`.

   | Child | Columns | Parent |
   | --- | --- | --- |
   | `page_translations` | `(page_id, site)` | `pages` |
   | `pages` | `(parent_id, site)` | `pages` |
   | `menu_items` | `(parent_id, site)` | `menu_items` |
   | `menu_items` | `(page_id, site)` | `pages` |
   | `menu_item_translations` | `(menu_item_id, site)` | `menu_items` |
   | `post_translations` | `(post_id, site)` | `posts` |
   | `category_translations` | `(category_id, site)` | `categories` |
   | `post_categories` | `(post_id, site)` | `posts` |
   | `post_categories` | `(category_id, site)` | `categories` |
   | `faqs` | `(page_id, site)` | `pages` |
   | `faq_translations` | `(faq_id, site)` | `faqs` |
   | `testimonial_translations` | `(testimonial_id, site)` | `testimonials` |
   | `lead_events` | `(lead_id, site)` | `leads` |

   Nullable child columns use `MATCH SIMPLE` (the default), so a NULL `page_id`/`parent_id` is not checked, as today. The constraints are created validated (not `NOT VALID`): every existing row is `43l`, so validation can't fail.
6. **`oauth_tokens`:** `account text NOT NULL DEFAULT 'default'` and a unique `(provider, account)` beside the primary key `provider`.
7. **Docs** (context, same change set as the spec PR's implementation): `07-data-model.md` "Multi-site" note gets the as-built migration number and the list above; `AGENTS.md` §3 Database row records `0014`.

### Dependencies & Risks

- **Depends on:** migrations `0000`–`0013` applied on production. `0013` (A-09 `site_settings.updated_by`) must be applied before `0014`; check it in `drizzle.__drizzle_migrations` first.
- **Blocked by questions:** none. Q-33 and Q-36 gate the AV launch (MS-08), not this additive step.
- **Risks:**
  - **Wrong rollout order:** deploying the new schema before `0014` exists in production makes Drizzle select missing columns, which breaks the CI build and the pages. Mitigation: migrate first (AC-10).
  - **Drizzle composite keys:** drizzle-kit may not express a foreign key to a non-primary unique key exactly as written. Mitigation: hand-check the SQL against AC-01, and adjust it by hand if needed, keeping `meta` snapshots consistent.
  - **Lock time:** `ADD COLUMN … DEFAULT` with a constant is metadata-only on Postgres ≥ 11, but it still takes an `ACCESS EXCLUSIVE` lock. New unique indexes and foreign-key validation scan their tables, and drizzle-kit runs the whole migration in one transaction, so every lock is held until commit. Table sizes are not known in this spec. Mitigation: the row counts and sizes step in Production rollout, the `lock_timeout` / `statement_timeout` header, and the rehearsal duration recorded in the PR. Run outside peak hours.
  - **Local dev points at production:** the `.env` `DATABASE_URL` is the production Supabase (owner rule). Rehearse only through `pnpm db:local` / `pnpm dev:local` (Docker on `localhost:54329`), never with `pnpm db:migrate` on the default env before AC-10.

### Production rollout (AC-10)

1. The rehearsal (AC-02…AC-07b, AC-04b) is recorded in the PR, including the migration's wall time on the upgraded local database.
2. **Sizes:** in the Supabase SQL editor (read-only), record `select relname, n_live_tup, pg_size_pretty(pg_total_relation_size(oid)) from pg_class where relname in (<listed tables>)` in the PR (counts only, no rows). If any table exceeds 100k rows, stop and re-plan (indexes `CONCURRENTLY` outside the transaction).
3. **Prerequisite:** `select id, hash, created_at from drizzle.__drizzle_migrations order by created_at desc limit 3` confirms `0013` applied.
4. The owner gives the go-ahead in the PR or chat.
5. **Backup:** Supabase dashboard backup or `pg_dump` (schema and data) to a local file outside git.
6. `pnpm db:migrate` with the direct connection, applying `0014` only. The migration starts with `SET lock_timeout = '5s'; SET statement_timeout = '60s';`. On a timeout the transaction rolls back by itself, nothing is applied, and `0014` is not recorded. Retry once at a quieter time; a second timeout stops the rollout for re-planning.
7. Smoke-check the **currently deployed** (old) app: `/`, `/gui-hang-di-singapore/`, `/admin/settings/` (open only), and one quote-form lead (then mark it spam in A-06). It must be unaffected.
8. Merge the PR. The deploy image build prerenders against the migrated database.
9. Smoke-check again after deploy, and record the date in AGENTS.md §3.

**Rollback:**
- **App rollback is the normal path.** Keep `0014` and redeploy the previous image (L-00 rollback by SHA). The old app ignores the additive columns (AC-04b), so the schema stays.
- **Schema reversal** only if the schema itself is wrong:
  1. Redeploy the baseline image first; the new schema code selects the columns.
  2. Drop the objects in reverse dependency order: composite foreign keys, then the site-inclusive indexes and `(id, site)` uniques, the `site` columns, `oauth_tokens.account`, and the type.
  3. Delete the `0014` row from `drizzle.__drizzle_migrations`.
  4. Revert the branch's schema and migration files.

  Reapplying later means generating a fresh migration. This is rehearsed on the local database before it is ever done on production.

### Implementation Hints

- **Drizzle:**
  - Declare the composite keys with `foreignKey({ columns: [t.pageId, t.site], foreignColumns: [pages.id, pages.site] })`.
  - Declare the parent uniques with `unique().on(t.id, t.site)` in the table's extra config, so drizzle-kit orders `UNIQUE` before the foreign keys that need it.
  - Keep the existing `.references()` calls: both foreign keys coexist until MS-03.
- **Enum name:** `site` is the Postgres type name. If it collides with a column name in generated SQL, name the type `site_code` (the column stays `site`).
- **Default:** `.notNull().default("43l")` on every new column. No backfill statement is needed.
- **Seed pattern:** the seed (`scripts/seed/write-routes.ts` `writeSettings`, the content writers) targets the old conflict keys. Leave them untouched; AC-04 proves they still work. MS-02 moves them to the new keys.
- **Lessons:**
  - `lessons/INDEX.md` 2026-10-23 s08-lead-form: specs miss files that a new prop or enum threads through. Grep `pgEnum` and `db/schema.ts` re-exports after adding the enum.
  - A repo-wide `lint:fix` rewrote unrelated files (Biome formats md and yaml). Run Biome only on changed paths.
- **Memory:** migrations drop things only after the deploy that stops using them. MS-01 drops nothing; MS-03 follows that rule.
